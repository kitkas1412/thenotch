# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`thenotch` is a macOS menu-bar-style app that renders a "Dynamic Island" around the MacBook notch (similar to DynamicLake). A black island sits over the notch and expands on hover; features are modules (Now Playing, Battery, Shelf, Volume & Brightness, Bluetooth, Notifications, AI Agents (Claude Code, Codex)). Releases are published on GitHub (see `CHANGELOG.md`).

## Commands

Shared scheme `thenotch` builds the app and runs the `thenotchTests` target (Swift Testing, hosted in the app). No linter or formatter is configured (swift-format may be installed locally, but the repo has no config — don't run it on the codebase). Baseline as of the System Monitor change: the Debug build takes ~8 s and has 5 compiler warnings, all in older code (`IslandEnvironment.swift` `@Entry` closure, `IslandController.swift` `NSEvent` Sendable, `SystemVolume.swift` `UnsafeRawPointer`, `NotificationBannerWatcher.swift` main-actor static, `NowPlayingService.swift` `NSImageRep`/`Task` Sendable) plus an `appintentsmetadataprocessor` tooling note; a new warning is a regression. The tests (348 Swift Testing tests in 49 suites) pass in ~10 s, and XCTest's "Executed 0 tests" line is expected. When piping `xcodebuild` output through `grep`/`tail`, use `set -o pipefail` so a failing run isn't masked.

```bash
# Build (Debug)
xcodebuild -project thenotch.xcodeproj -scheme thenotch -configuration Debug build

# Run all tests (same command CI uses)
xcodebuild test -project thenotch.xcodeproj -scheme thenotch -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO

# Run a single test / suite
xcodebuild test ... -only-testing:thenotchTests/NotchGeometryTests/notchedScreenUsesAuxiliaryAreas
```

Releases: `scripts/build-release.sh [version]` builds a universal, ad-hoc-signed, stripped Release (`DEPLOYMENT_POSTPROCESSING`/`STRIP_INSTALLED_PRODUCT` in the Release configuration, since the script runs `xcodebuild build`, not `archive`; the dSYMs stay in the build folder) (entitlements from `scripts/release.entitlements`, no `get-task-allow`) into `dist/` as DMG + zip. Pushing a `v*` tag runs `.github/workflows/release.yml`, which publishes a GitHub Release using the matching `CHANGELOG.md` section; the tag must match `MARKETING_VERSION`.

CI (`.github/workflows/ci.yml`) runs the test command on every push to `main` and every PR, on the `xcode-27` runner image. Test logs are noisy with `com.apple.linkd.autoShortcut` connection errors; they are harmless.

Keep testable logic as pure functions taking plain values (see `NotchGeometry.notchRect(frame:visibleFrame:topInset:leftArea:rightArea:)`), with a thin `NSScreen` wrapper — `NSScreen` can't be constructed in tests.

Run the app from Xcode (⌘R). Because of `LSUIElement`, it has no Dock icon or main window — quit it from its menu bar icon (capsule) → Quit, or `killall thenotch`. Run one copy at a time (a copy started with `open` and one from Xcode both tap keys, watch Notification Center and listen on the Claude Code socket). With Volume & Brightness on, a copy paused in the debugger (a breakpoint, a crash) holds up every key press and pointer event for about a second, system-wide: its key tap can't answer. Stop or quit it.

## Architecture

- **Entry point** (`thenotch/App/`): `thenotchApp` declares a `MenuBarExtra` (`.window` style, hosting `App/MenuPanel`: the System Monitor section while that tool is on, then Settings…, Check for Updates…, Quit rows; the rows that open a window or app close the panel first) and a `Settings` scene, and hands control to `AppDelegate` via `@NSApplicationDelegateAdaptor`. `AppDelegate` owns `AppSettings`, `Updater`, the `HotKeyCenter`, the `SystemSampler` (`systemMonitor`) and the `ToolHost`, and starts the host in `applicationDidFinishLaunching`. `App/AppIdentity` holds the name and bundle-derived strings (name, `bundleID`, queue label prefix and `queueLabel(_:)`, log subsystem, `supportDirectory`, `hookSourcePrefix`, hooks `backupExtension`): use it instead of literals, so a rename edits one file. The island itself is driven from AppKit, not SwiftUI scenes — do not add a `WindowGroup`.
- **Tools** (`thenotch/Tools/`, `App/ToolHost`): the app is a suite of tools. A `Tool` (`@MainActor` protocol: `id`, `start()`, `stop()`) is built from a `ToolKind` (`makeTool(context:)` with a `ToolContext { settings, hotKeys, systemMonitor }`; `rawValue` must equal the tool's `id`). `ToolKind` has `.notch` (on by default), `.systemMonitor` and `.windowManagement` (off). To add a tool, add a case to `ToolKind` (title, symbol, summary, `makeTool`), a pane in `Settings/Panes/` and a case in `SettingsView`'s detail switch. `ToolHost` builds every tool at init, starts the enabled ones in `ToolKind` order and stops them in reverse; the switch `tool.<id>.enabled` (`AppSettings.setToolEnabled`, `onToolsChange`) starts or stops a tool while the host runs. Tools are never started under a host that was not started.
- **Settings** (`thenotch/Settings/`): `SettingsView` is a `NavigationSplitView` in the `Settings` scene: a sidebar with General and, under Tools, one entry per `ToolKind` (icon tile from `SettingsIconTile`). The selected pane is stored in `@AppStorage("settings.pane")` as `SettingsPane.storedValue`: `general` or `tool.<id>` (the legacy `modules` opens Notch; anything unknown, General). Panes live in `Settings/Panes/` (`GeneralPane`, `NotchPane`, `SystemMonitorPane`, `WindowManagementPane`), shared views in `Settings/Components/` (`SettingsToggleRow`, `SettingsNote`, `SettingsNotice` with a symbol and the action that fixes it, `ShortcutRecorder`/`ShortcutRow`): grouped forms with small controls, each tool or module a section with its icon tile and a regular switch, its options shown under it only while it's on. `NotchPane` shows the Notch switch, the shortcuts, then the modules; while Notch is off the module sections are hidden (a module can only be turned off while the island runs, which removes its hooks).
- **Platform services** (`thenotch/Platform/`), shared by tools:
  - `Permissions/PermissionCenter` — `Permission` (Accessibility, Screen Recording, Input Monitoring, Automation, Bluetooth) with `status(_:)` (never prompts; Automation is `.unknown`, it is per target app), `request(_:)` (may prompt; Automation opens its pane) and `openSettings(_:)`. The Accessibility modules, Window Management and the Bluetooth module still use `AccessibilityPermission` and `BluetoothPermission`.
  - `Input/Shortcut` + `Input/HotKeyCenter` — global shortcuts through Carbon `RegisterEventHotKey` (no permission). `Shortcut` is a pure value (Carbon key code and modifiers, `displayString` in ⌃⌥⇧⌘ order); `validation` needs ⌘ or ⌃ unless it is an F-key, and refuses reserved macOS combos (Spotlight, App switcher, Screenshot…). `HotKeyCenter` registers handlers under a string id with one lazily installed event handler (removed when no entry is left); `RegistrationResult` is `registered`, `unavailable` (another app has it) or `invalid`; `suspend()` releases every hotkey while a `ShortcutRecorder` captures keys and `resume()` brings them back, retrying the unavailable ones; `conflictingID(for:excluding:)` finds another of our actions on the same shortcut. `ShortcutAction` (id, title, owning `ToolKind`, `defaultShortcut`) lists the actions in `ShortcutAction.all`; `actions(for:)` gives one tool's. They are `notch.toggle` (unbound by default) and `windows.<WindowAction>` (the 17 Window Management actions). `AppSettings` keeps the effective shortcut per action (`shortcut(for:)`, `nil` when unbound): the default until the user records one (stored as JSON under `shortcut.<actionID>`, `setShortcut`), or none once cleared (stored as JSON `null`, so the default doesn't come back). `resetShortcut(for:)` removes the stored value and goes back to the default. `observeShortcuts(_:)` returns a `ShortcutObservation` token that calls back with the action id after a shortcut really changed; it is held weakly, so keep the token while observing, and `cancel()` (or releasing it) stops the calls. `NotchTool` registers `notch.toggle` while it runs and calls `IslandController.toggleFromShortcut()` (opens like a click, or closes; ignored while not started, hidden, dragging or a menu is tracked).
  - `Accessibility/AXWindow` — the focused window of the frontmost app, read and moved through the Accessibility API (needs `AccessibilityPermission`; our own app is skipped). Frames are in AX coordinates; every call is bounded by a 0.25 s messaging timeout. `setFrame` sets size, position, then size again (the first size can be clamped by the display the window is on); a window that can't be moved returns `false`, and one that can't be resized is only moved.
- **Notch tool** (`Tools/Notch/NotchTool`): owns the `IslandController`. `start()` starts it, registers the shortcut and re-registers it when the user changes it (`observeShortcuts`); `stop()` unregisters it and calls `IslandController.stop()`, which closes the island, removes every monitor and observer, cancels pending work and calls `suspend()` on the modules, so Notch off leaves nothing running. `IslandController.start()`/`stop()` are guarded and restartable (a new start begins afresh). `IslandModule.suspend()` defaults to `stop()`; `ClaudeCodeModule.suspend()` stops listening but keeps the hooks, which `stop()` (AI Agents turned off) removes. `ShelfModule` sweeps orphaned dropped files once per process, not on each Notch off/on.
- **Intended flow** (`thenotch/Core/`):
  - `Window/IslandController` — created by `NotchTool`; owns the panel, positions it over the notch, reacts to screen changes.
  - `Window/IslandPanel` — borderless, non-activating `NSPanel` sitting at/above the menu bar level, hosting SwiftUI via `NSHostingView`.
  - `Geometry/NotchGeometry` — computes the notch rect from `NSScreen` (`safeAreaInsets`, `auxiliaryTopLeftArea` / `auxiliaryTopRightArea`); on screens without a notch it returns a simulated 190pt-wide notch under the menu bar. `targetScreen()` prefers the notched display.
  - `State/IslandState` — observable model (collapsed/expanded, content) shared between controller and views.
  - `State/HoverPolicy` — pure decisions from the pointer position, with hysteresis (exit region larger than entry). Hovering never opens the island: `hoverAction` sets `IslandState.isHovering` (only while some module has expanded content), which grows the island by `IslandStyle.hoverScale` (`scaleEffect` anchored at the top; under Reduce Motion a `Size.hoverBorder` outline instead) and makes the panel accept mouse events; it ends outside `hoverExitRect` (the grown size). A click opens it: a local `leftMouseDown` monitor on the panel feeds `clickAction` (open/close/none); the open island closes on a click outside (global monitor), a click on the notch, or Esc (global `keyDown` monitor, needs Accessibility, started on open and when Accessibility changes), not when the pointer leaves. The controller feeds `hoverAction` from a global `mouseMoved` monitor plus an `.activeAlways` tracking area on the hosting view (AppKit only sends `mouseMoved` to the key window, and the panel never becomes key); hover is re-evaluated when module settings or the expandable content change (`observeExpandableContent`) and once after the island closes. Only a file drag opens and closes by position (`dragAction`; `closeIfDragLeft()` after it).
  - `Modules/IslandModule` + `State/ActivityCenter` — features are `IslandModule`s. To add one, add a case to `ModuleKind` (`thenotch/Settings/AppSettings.swift`); its `rawValue` must equal the module's `id`. `IslandController.applyModuleSettings()` starts/stops modules as they're toggled in Settings. A module publishes a `LiveActivity` (priority, optional expiry, `presents` to open the island by itself) to `state.activities`; `ActivityCenter` picks the one shown in compact mode, and `IslandView` renders that module's `compactLeading`/`compactTrailing` wings beside the notch and its `expandedView` when open. A module reports `hasExpandedContent` (hovering grows the island, and a click opens it, only if some module has content; `IslandState.expandedModule` is `nil` otherwise) its `compactContentWidth` (wings are that wide plus equal padding, `IslandState.compactPadding`), When two or more modules have content, `IslandView` shows a tab per module left of the notch (`IslandState.showsTabs`, `select(_:)` re-pins until the island closes). Each module also reports its `expandedContentHeight` (content only, with its bottom margin; `IslandState.expandedSize` adds the notch height, the margin below it and, when the tabs don't fit beside the notch, the tab row; the total must stay ≤ `IslandController.panelSize.height`) and may report a narrower `expandedWidth` (default `IslandState.expandedWidth`). `islandDidCollapse()` runs for every module when the island closes. While a file drag has the open island shrinking under the pointer (a narrower tab), `HoverPolicy.ShrinkGrace` keeps the old region open until the pointer is back over it (only the drag path uses it).
  - **File drops**: a module conforming to `FileDropReceiving` (the Shelf) takes files dropped on the island. The controller watches global `leftMouseDown/Dragged/Up` events; near the notch it checks the drag pasteboard (`FileDrag`: `changeCount` must have changed since mouse-down, since the pasteboard keeps the previous drag's contents) and opens the island pinned to that module, using the wider `HoverPolicy.dragEntryRect`. `IslandView`'s `onDrop` loads them via `FileDrop` as `DroppedFile`s: file URLs are referenced, other content (file promises, images…) is saved into `Application Support/<bundle id>/Dropped/<uuid>/` and marked `isOwned` — the Shelf deletes those folders when the item leaves, and orphans at start. The shelf persists as `Shelf.json` (bookmarks) via `ShelfPersistence`, read in the background at start (`ShelfStore.load()`; nothing is saved before it finishes) and written on a background queue 1 s after the last change (`ShelfStore.saveNow()` flushes on quit and when the module stops); Quick Look thumbnails are cached in `ShelfThumbnails` (keyed by size too); the shelf opens as a square stack (`ShelfStackView`, 256 pt wide: newest files fanned out, ✕ Clear and … More (an `NSMenu`) in a row above it, "Show All" centered below, or a small AirDrop drop zone when empty; "Drop here" while files are dragged in) and widens to the list (`ShelfListView`) through `ShelfPresentation.showsAll` until the island closes; expiry (`AppSettings.shelfLifetime`) uses one sleeping task, not polling; while files are dragged in, `IslandView` draws the island's border (thick and white once they're over it and not over a zone, `\.isIslandDropTargeted`) and a drop anywhere outside a zone goes to the shown module; modules read `\.isDraggingFiles` from the environment to show their own drop zones (`IslandDropZone`s, which only report their frames: `IslandView` has the single `onDrop`, outside the clip shape, and routes files to the zone under the pointer; an `onDrop` inside the clipped island gets a misplaced AppKit view and never receives drops). Dragging out: shelf tiles (and the stack, which drags every file) start an AppKit dragging session (`ShelfDrag`, so Finder can *move* the file and we learn the operation; SwiftUI's `onDrag` only copies). Any completed drop removes the item from the shelf (`ShelfDrag.Outcome`); after a copy (a browser upload, Mail…) its owned file is kept for the next launch's orphan cleanup, since the app may still be reading it and call `\.beginDragOut`; the island stays open until the mouse button is released (polled). It also stays open while one of our menus tracks (`NSMenu.didBeginTracking`).
  - `State/AmbientConditions` — display asleep, screen locked, session inactive, Low Power Mode; the controller keeps `state.ambient` current and views read `\.allowsAmbientAnimation` to stop ambient animation (the level meter).
  - `UI/IslandView` + `UI/NotchShape` — SwiftUI rendering of the island and its notch-matching shape. The island is always black: it renders under a forced dark color scheme, so views use semantic styles (`.primary`, `.secondary`) rather than `.white.opacity(…)`. The design system is documented in `DESIGN.md`: tokens in `Core/UI/DesignSystem/` (`IslandStyle` spacing/radius/size/symbol sizes/motion, `IslandColors` with `IslandFill` levels that strengthen under Increase Contrast and `IslandSignal` status colors, `IslandTypography` `Font.island*` styles) and shared views in `Core/UI/Components/` (`.islandIcon`/`.islandText` button styles, `IslandEmptyState`, `IslandDropZone`, `IslandProgressBar`, `.islandContentMargins()`). Views use these tokens, not literal sizes, opacities or colors.
- **Feature modules** live in `thenotch/Modules/<Name>/` (service + module + views). `NowPlaying` combines `NowPlayingService` (state from Spotify/Music notifications, AppleScript controls, artwork cache) with compact wings (artwork, level meter tinted by `ArtworkTint`) and an expanded player: a progress bar that seeks on click or drag (`set player position`, applied at once and re-read if the app refuses; the island stays open until the button is released), a Music-only favorite star (`favorited`, falling back to `loved` on older Music; Spotify's scripting can't set it) and an audio output picker (`AudioOutputs`, CoreAudio, read when the island opens).
- **Volume & Brightness** (`Modules/HUD`, `ModuleKind.hud`, off by default: `ModuleKind.isOnByDefault`): `MediaKeyTap` is a Quartz event tap on its own thread (it sees every key press, and macOS waits for it, so typing must never wait on the main thread; `HUDKeys.handle` acts on the key there, CoreAudio and DisplayServices being thread-safe, and only the display hops to the main queue) (needs Accessibility, `AccessibilityPermission`, asked for when the module is turned on in Settings) that takes the volume, mute and brightness keys (`.systemDefined` events, `MediaKey.press(subtype:data1:)`, plus key codes 144/145) and returns whether they were handled — handled keys (press and release) never reach macOS, so its overlay doesn't show. Volume uses CoreAudio (`SystemVolume`, the default output's `VirtualMainVolume`/mute), brightness the private DisplayServices framework loaded with `dlopen` (`DisplayBrightness`, built-in display only). Keys it can't act on (no settable volume, no built-in display, the framework missing, Option alone) pass through. Steps follow macOS: 1/16, 1/64 with Shift-Option (`MediaKey.step`). The level shows as a `LiveActivity` (priority 60, 1.5 s) with a symbol and an `IslandProgressBar`; no expanded content. The tap retries when `com.apple.accessibility.api` is posted.
- **Bluetooth** (`Modules/Bluetooth`, `ModuleKind.bluetooth`, off by default): `BluetoothService` reports a device on two events: an IOBluetooth connect notification (devices already connected at start are skipped; disconnects are watched per device), and the default output moving to a Bluetooth audio device (a CoreAudio listener; the UID, e.g. `F8-1E-49-A0-34-A8:output`, holds the address: `BluetoothDevice.address(fromAudioUID:)`) — AirPods often stay connected in their case, so taking them out only moves the sound. IOBluetooth calls back on the main thread *or* its own queue (the same connection arrives on both), so the callbacks are `nonisolated` and hop to the main queue. Addresses are compared `BluetoothDevice.normalized`; a second event for the device already peeking only updates it. The first IOBluetooth use asks for Bluetooth permission (`NSBluetoothAlwaysUsageDescription`; `BluetoothPermission` reads `CBManager.authorization` for Settings). Battery levels are `IOBluetoothDevice`'s non-public `batteryPercentSingle/Left/Right/Case` read only if it `responds(to:)` (0 = unknown), else the HID service's `BatteryPercent` in the I/O Registry (Magic devices); they're read again after 1 s and 3 s, since AirPods report late. A connection is a 4 s peek (`LiveActivity` priority 50): symbol (`BluetoothDevice.symbol`, Apple product IDs then device class) and the lower bud's level beside the notch, name and every battery in the open island.
- **Notifications** (`Modules/Notifications`, `ModuleKind.notifications`, off by default, needs Accessibility like the HUD: `ModuleKind.needsAccessibility`): replaces the macOS banners. There is no API for other apps' notifications; `NotificationBannerWatcher` observes Notification Center (`com.apple.notificationcenterui`) with an `AXObserver` (window created / created / layout changed, on the main run loop, 0.25 s messaging timeout; re-attached when Notification Center relaunches or access changes), copies the window into a plain `AXNode` tree and lets `NotificationBanners` (pure) decide: a window with `AXNotificationCenterBanner`s is a banner window — unless it holds Notification Center's panel (`AXNotificationListItems`) or a persistent banner (`AXNotificationCenterAlert`), which are left alone. It moves a banner window off screen (`AXPosition`; the `Close` action only takes effect after the banner has slid in, so it's visible for a second or two; each banner gets a new window, so nothing is restored), which keeps the notification in Notification Center. Only the texts the banner shows (`title`, `subtitle`, `body` identifiers) are read, so Show previews applies (the body is a placeholder); the banner's `AXDescription` has the full text even then, so only the app's name (its first part) comes from it. `RecentNotifications` keeps the last 3, in memory, cleared once the island has shown them; a new one is a 2 s `LiveActivity` (priority 55, the app's icon from `NotificationApps`, found by name) that `presents`: `ActivityCenter.onPresent` makes `IslandController.present(_:)` open the island pinned to it until it expires — not over an island the user opened, a drag or a menu, nor while `AmbientConditions.isVisible` is false; it ends by itself (`endPresentation()` closes the island) unless the user clicked the island meanwhile (`Presentation.isOwnedByUser`): from then on they close it. Clicking a row presses the banner (`AXPress`, opens the app on that notification) while it exists, else opens the app. Calls: a persistent alert with accept and decline actions is a call (`CallAlerts`, pure; action names are localized, `Name:Accept\nTarget:…`); its window is moved off screen while it rings and put back on stop, the alert is re-read every 0.5 s to see it end, and the call is a `LiveActivity` without expiry (priority 80) that `presents`: the presentation lasts until the activity is removed (`ActivityCenter.onRemove`), and a brief activity doesn't cut it short. The island shows the caller with Decline/Accept (`IslandSignal.callDecline`/`callAccept`), which perform the alert's actions. Debug builds launched with `-debug.fakeCall '<true/>'` show a fake call. macOS 26's `com.apple.ncprefs.plist` isn't updated by System Settings any more: don't read styles or preview settings from it. Logs never contain the text.
- **AI Agents** (`Modules/ClaudeCode`, `ModuleKind.claudeCode`, display name "AI Agents", off by default): shows Claude (the Claude Code CLI and the Claude desktop app's Code tab) and Codex (the Codex CLI and Codex in the ChatGPT app). Turning it on adds user-level hooks to `~/.claude/settings.json` (`ClaudeHooksConfig`) and, only if `~/.codex` exists, to `~/.codex/hooks.json` (`CodexHooksConfig`; `config.toml` is never touched). Codex asks the user to trust new hooks once (`/hooks` in the CLI, Settings › Hooks in the ChatGPT app), and a Codex installed later is picked up by turning the module off and on. Both share `AgentHooksFile`: one `matcher: ""` command per event in `events`, `{ printf 'thenotch-source: <claude|codex>\n'; cat; } | /usr/bin/nc -U -w 1 '<socket>' … || true`, so the agent never fails on a closed thenotch; `AgentSource.split` reads the first line (a payload without it, from an older install, is Claude's). Merged into the existing JSON; valid JSON of an unexpected shape (`unexpectedShape`) or invalid JSON is left alone; written atomically through symlinks keeping the file's POSIX permissions, the original copied once to `<file>.thenotch-backup`; hooks are found again by the socket path (an older command is replaced) and removed when the module is turned off. Claude's hooks are async (`ClaudeHooksConfig.usesAsync`); Codex's are synchronous (`CodexHooksConfig.usesAsync = false`) because Codex releases before rust-v0.148.0 silently skip async command hooks (github.com/openai/codex/releases/tag/rust-v0.148.0, learn.chatgpt.com/docs/hooks). A sync hook is cheap: macOS `nc -U -w 1` half-closes on stdin EOF, so it returns in about 30 ms (measured). Don't add `-N` to the command: on macOS nc it is a probe count, not shutdown-on-EOF, and it would break the hook silently. `ClaudeHookServer` listens on `Application Support/<bundle id>/claude-hooks.sock` (0600), reads each connection off the main thread and hands a `ClaudeHookEvent` to the main queue — only the event name, source, session, cwd, tool name and notification type/message are kept, never prompts, replies, tool input or `AskUserQuestion`'s questions. `ClaudeSessions` (pure; keyed by source and session ID, so IDs can't collide) turns events into per-session states (working, needs permission, asking, waiting for input, idle; Codex's `PermissionRequest` is needs permission; stale ones pruned; `.working` and `.needsPermission` settle to idle after `workingTimeout`, 30 min, since a denial isn't reported). An asking session's row says "Has a question — answer in <Source>" (hooks can't answer). `turnStartedAt` is set by `UserPromptSubmit` (a new prompt restarts it) and cleared on Stop. Activities: a lasting one while a session works (priority 8, under Now Playing) or waits for permission or an answer (70), and a 4 s peek (`<id>.peek`, 50) when a reply finishes or a session asks for input; the open island lists the sessions, each with its source name and, while working, its turn time. The left wing shows the `sparkle` symbol, pulsing while a session works; the right wing shows the longest working session's turn time (`AgentElapsed.format`, `m:ss`, `h:mm:ss` from an hour; the wing width is `IslandStyle.Size.compactElapsed` while any session works, even during a peek), ticking every second only while `allowsAmbientAnimation`. Source names are plain text only. (Don't use Anthropic's or OpenAI's logos or the Claude Code mascot: their trademark guidelines need prior approval, and releases are public.)
- **System Monitor** (`Tools/SystemMonitor/`, `ToolKind.systemMonitor`, off by default; public APIs only, no extra permission; temperatures and fan speeds aren't shown): CPU, memory, network and disk. `SystemMetrics.swift` is pure (testable on plain values): `CPUUsage`/`CPUTicks`, `MemoryUsage` (active + wired + compressed pages), `NetworkRate`, `DiskUsage`, `MetricFormat` (decimal units) and `NetworkInterfaces`, which sums the `NET_RT_IFLIST2` counters of every interface that is up and not loopback, except those whose name starts with `lo`, `utun`, `ipsec`, `ppp`, `awdl`, `llw`, `bridge`, `ap`, `gif`, `stf`, `anpi`, `vmenet` or `feth` (virtual, tunnel and peer-to-peer interfaces, so VPN traffic isn't counted twice); `en*`, `pdp_ip*` and any other name count. `SystemReader` (an `actor`, `SystemCalls` holds the Mach/sysctl/volume calls) returns a `SystemSnapshot`. `SystemReader` (an `actor`, `SystemCalls` holds the Mach/sysctl/volume calls) returns a `SystemSnapshot`. `SystemSampler` (`@Observable`, created by `AppDelegate` and passed as `ToolContext.systemMonitor`) publishes the snapshot and reads it every `interval` (1 s), only while `SystemSampling.shouldSample` holds: the tool is on (`isEnabled`, set by `SystemMonitorTool`'s start/stop), the menu panel is visible (`isPanelVisible`, set by `PanelWindowTracker` in `App/MenuPanel.swift` from the panel window's key, occlusion and close notifications) and `AmbientConditions.isVisible` (display awake, screen unlocked, session active; the lock state comes from the distributed `com.apple.screenIsLocked`/`screenIsUnlocked` notifications, there is no public API). Enabling seeds those conditions from `CGDisplayIsAsleep` and `CGSessionCopyCurrentDictionary`. The first reading only primes the deltas and isn't published; when sampling stops the snapshot is reset to empty, so the next open shows placeholders, not an earlier reading. `SystemMonitorSection` draws the top of the panel: CPU, memory, network down/up and disk free, each showing "—" until the second reading, then Open Activity Monitor. There are no settings: the Settings pane is the switch and short notes. The tool's UI is menu panel chrome, so it uses system fonts, colors and controls, not the Island tokens (see `DESIGN.md`).
- **Window Management** (`Tools/Windows/`, `ToolKind.windowManagement`, off by default; needs Accessibility, `AccessibilityPermission`, asked for when the tool is turned on in Settings): `WindowAction` has 17 actions, each with a default ⌃⌥ shortcut: arrows for halves, U/I/J/K for quarters, D/F/G/E/T for thirds, ↩ maximize, C center, and ⌃⌥⌘→/← for the next/previous display. `WindowLayout` is pure and works in Cocoa coordinates (origin bottom left): placements fill the screen's `visibleFrame` and are rounded to whole points; `axToCocoa`/`cocoaToAX` flip against the primary screen (the one whose origin is `.zero`). The window's screen is the one it overlaps most (`screenIndex`, else the nearest center). A display action keeps the window's relative position and size, scaled to the target (`movedToDisplay`), or fills the target's visible area if it doesn't fit. `WindowManagerTool` registers its hotkeys only while Accessibility is trusted: at start, on the Accessibility change notification (re-checked a second later, since the notification can arrive first) and on app activation; turning the tool off unregisters them. It beeps when there is no focused window or the move fails; full-screen windows, windows without a readable frame, and display actions with a single display do nothing.
- **Updates** (`App/Updater`): Sparkle 2 via SPM; `SPUStandardUpdaterController` is not started under unit tests. `SUFeedURL`, `SUPublicEDKey` and the daily automatic check (`SUEnableAutomaticChecks`, `SUScheduledCheckInterval` = 86400) live in `Config/Info.plist` (merged into the generated Info.plist; kept outside `thenotch/` so the synchronized group doesn't copy it). The Release workflow signs the zip with the `SPARKLE_PRIVATE_KEY` secret and attaches `appcast.xml` (`scripts/make-appcast.sh`); each release needs a higher `CURRENT_PROJECT_VERSION`. Ad-hoc releases need `com.apple.security.cs.disable-library-validation` (`scripts/release.entitlements`): without a Team ID, the hardened runtime refuses to load the embedded Sparkle.framework and the app won't launch; drop it once releases use a Developer ID. Debug builds are team-signed and don't need it.
- The Xcode project uses **file-system synchronized groups**: any file added under `thenotch/` is automatically part of the target; no `project.pbxproj` edits are needed when adding/moving files.

## Build settings that matter

- **App Sandbox is OFF** and Hardened Runtime is ON — intentional, because notch apps need system-level access (media info, screen/window APIs). Distribution is outside the Mac App Store (notarization).
- **Deployment target: macOS 14.0** (target-level setting overrides the project-level 26.6). Guard newer APIs with `#available`.
- **Swift 5 language mode, `SWIFT_DEFAULT_ACTOR_ISOLATION = nonisolated`, approachable concurrency OFF.** Types are *not* implicitly `@MainActor`, so mark AppKit/SwiftUI-facing types (`AppDelegate`, `IslandController`, `IslandPanel`, `IslandState`) with `@MainActor` explicitly.
- **Automation (Apple Events)** is enabled via `AUTOMATION_APPLE_EVENTS = YES` (hardened-runtime entitlement) and `INFOPLIST_KEY_NSAppleEventsUsageDescription`. Now Playing reads state from Spotify/Music distributed notifications (no permission) and uses AppleScript only for controls/position; never script an app that isn't running (`tell application` would launch it). Permission sticks only with a stable signing identity (your Apple Development team), not ad-hoc signing.
- Info.plist is generated (`GENERATE_INFOPLIST_FILE = YES`); add keys via `INFOPLIST_KEY_*` build settings rather than a plist file.

## Git workflow

`main` is protected: never commit or push to it directly. Work on a new branch (`<type>/<topic>`, e.g. `feat/island-panel`), push it, and open a PR. A PR may only be merged once every CI check (`build-and-test`) passes. Commit messages follow Conventional Commits (`feat:`, `fix:`, `docs:`, `ci:`, `chore:` …).

The `/ship` skill (`.claude/skills/ship/`) automates branch → test → commit → push and stops there. A `PreToolUse` hook (`.claude/hooks/block-main-commits.sh`, needs `jq`) blocks `git commit`/`git push` on `main`; direct `gh pr create` and `gh pr merge` are denied in `.claude/settings.json`. The repo is registered with `~/.claude/hooks/git-publish.sh` at level `merge` (Conventional Commits; CI-file changes refused): the orchestrator's `release-manager` may open a draft PR and squash merge only through that script, only when the approved plan includes it, only after every CI check (`build-and-test`) passes, and only after the maintainer confirms the merge. PR bodies follow `.github/pull_request_template.md` (Summary, Test plan, Notes).

`.agents/skills/ship/` is the Codex copy of `.claude/skills/ship/`; keep both in sync. `.codex/hooks.json` uses an absolute path (`/Users/neco/Developer/thenotch/.codex/hooks/...`), so it is not portable.
